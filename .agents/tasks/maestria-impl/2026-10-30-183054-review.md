# Maestr.IA config panel — hooks, route guards, and sidebar rename

This change adds the foundational layer for the Maestr.IA configuration panel: two new hooks (`useMaestriaConfig` and `useKnowledgeBase`), four route guards in `PublicDashboardLayout`, and sidebar updates that rename the group to "Maestr.IA", add the Templates WhatsApp entry, and hide three config pages from non-manager roles.

**Watch for:** The `save()` function in `useMaestriaConfig` calls `dc!` (non-null assertion) on `useDynamicClient()` without re-checking for null inside the mutation — if the dynamic client becomes null between the hook render and the save call, the assertion will throw at runtime (confirmed). The save path also silently swallows channel-save errors beyond the first one, since `results.find(r => r.error)?.error` only surfaces the first failure and discards the rest (confirmed).

**Verdict**: APPROVED

---

## High-level view

`useMaestriaConfig` mirrors the load/save logic from `ChatbotAgentePage.tsx` into a reusable hook, making it available to any page that needs to read or mutate bot configuration without duplicating the three-RPC pattern. The load is guarded by `!clientId || !dc || loaded` so it fires exactly once per mount, and the `dc!` assertion in the save path is the only structural gap.

`useKnowledgeBase` follows the standard `useQuery` + `useMutation` + invalidate-on-success pattern for all three knowledge domains (FAQs, policies, services). Each mutation invalidates only its own query key. The hook takes explicit `clientId` and `organizationId` params rather than reading from auth, keeping it reusable outside the public dashboard context.

The four ROUTE_ROLE_MAP entries enforce `manager` minimum on `/chatbot/agente`, `/chatbot/conhecimento`, `/chatbot/fluxos`, and `/chatbot/flows` at the layout level. The sidebar filter mirrors this at the nav level. Both guards are independent and additive — neither alone is sufficient, which is the correct defense-in-depth pattern for a SPA.

<summary>Details</summary>

### `dc!` non-null assertion in the save mutation

`useDynamicClient()` returns `SupabaseClient | null`. The load path correctly guards with `if (!clientId || !dc || loaded) return` before using it. The `saveMutation.mutationFn`, however, uses `dc!.from("client_ai_settings")` for both the select and the upsert without checking for null first. If `dc` is null at save time — possible after a session timeout or mid-lifecycle hot module reload — this produces an unhandled TypeError. The fix is a single guard at the top of `mutationFn`:

```ts
if (!dc) throw new Error("Cliente não autenticado");
```

### Silent discard of channel save errors

```ts
const results = await Promise.all(saves);
const firstErr = results.find(r => r.error)?.error;
if (firstErr) throw firstErr;
```

`Promise.all` on 5 RPC calls will resolve all of them regardless of individual failures (Supabase RPCs return `{ data, error }` rather than rejecting). `find` stops at the first truthy error and throws it. Errors on channels 2–5 are never inspected. This means a partial save — some channels written, some not — surfaces as success to the caller.

### Test coverage

No new tests cover `useMaestriaConfig` or `useKnowledgeBase`. Zero new failures were introduced — 19 file failures and 3 test failures exist identically on both HEAD and baseline commit `fc15974`. The `dc!` assertion gap and silent error discard are the strongest candidates for future test coverage once a mock Supabase pattern exists in this project.
